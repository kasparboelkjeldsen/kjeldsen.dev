This Blog Was Built Without Opening the Backoffice

What it looks like when a CMS speaks MCP and an agent is handed the keys.

The brief

The instruction was one paragraph: spin up a simple blog, build everything with blocks and the block grid, and write two posts about why MCP is awesome. You are reading the second one.

What the agent actually did

  1. Modeled the content. Five element types (hero, rich text, image, quote, post list), a block grid data type that allows them, and two page types with templates.
  2. Filed everything where it belongs. Blocks went into the Blocks folder and pages into Pages, following the project's own rules.
  3. Pulled in media. Images were streamed from Unsplash straight into a media folder.
  4. Wrote and published. A front page and two posts, each assembled from blocks, plus a domain so the site answers on the root url.

Every one of those steps was an MCP tool call against the Umbraco Management API.

Why this matters for a CMS

  • The boring parts disappear. Scaffolding document types and seeding realistic content takes minutes.
  • It is real content. Nothing here is a mock-up. Editors can open any page in the backoffice and keep working on it, block by block.
  • The rules still apply. The agent works through the same API, permissions and validation as everyone else, and the project conventions are written down where it can read them.
  • It is verifiable. Every write can be read back. When a payload is wrong, the agent sees that and corrects it.

The takeaway

MCP does not replace the editor or the developer. It removes the distance between deciding what should exist and having it exist. That is why it is awesome.
