One Protocol to Connect Them All

Why the Model Context Protocol is the boring, open standard AI tooling has been missing.

The integration problem nobody wanted to keep solving

Every AI assistant that has needed to reach outside its own context window has done it the same way: someone wrote a bespoke connector. One for the ticket tracker, one for the database, one for the CMS — each with its own auth dance, its own schema and its own failure modes. Multiply that by every model vendor and every tool, and you get an M×N integration matrix that never stops growing.

The Model Context Protocol collapses that matrix. A tool exposes itself once, as an MCP server. Any MCP-capable client — a coding agent, an IDE, a desktop app — can then discover what it offers and use it. M×N becomes M+N.

What an MCP server actually gives you

  • Tools — typed, described operations the model can call, like create-document or get-document-type-by-id.

  • Resources — read-only context the client can pull in on demand.

  • Prompts — reusable, parameterised workflows curated by the server author.

Because every tool ships with a JSON Schema, the model knows exactly which arguments are valid before it calls anything. No scraping docs, no guessing at payloads.

Why this matters more than it looks

The real win isn't convenience — it's composability. An agent with an Umbraco MCP server, a Git server and a browser server can model content, commit the schema and check the rendered page in one continuous loop, without anyone writing glue code between them.

And because the protocol is open, the investment is portable. The MCP server you write for your product today works with tomorrow's clients too. That is the kind of durable, unglamorous standard the AI tooling world has badly needed.

Write the integration once. Let every agent use it.
