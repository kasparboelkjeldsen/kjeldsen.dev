5 Reasons MCP Changes How We Build With AI

MCP has been out long enough to stop being a novelty and start being infrastructure. Here are five reasons it's earned a permanent spot in how we build AI-assisted tools — drawn straight from building this very blog with it.

1. One protocol, any tool

A single MCP client can talk to a filesystem server, a database server, and a CMS server like Umbraco's without custom adapters for each. The client learns capabilities at runtime instead of baking in assumptions at build time.

2. Schemas the model can actually read

Every tool ships a JSON schema for its inputs. That turns "hope the model formats this right" into "validate before you call it" — the difference between a flaky demo and something you'd run unattended.

3. Local-first by default

The reference transports are stdio and local HTTP. Your data doesn't need to leave the machine for the model to act on it — the Umbraco MCP server used to build this site never left localhost.

4. Composable agents

Because servers are interchangeable, an agent's capability set is just "which servers are attached today." Add a server, gain a skill — no redeploying the assistant.

5. It documents itself

Tool descriptions double as onboarding docs for both humans and models. Reading this project's MCP configuration and tool list tells you almost everything about what the assistant is allowed to touch.

“The best integrations are the ones you don't have to write twice.”

— Every engineer who has maintained two SDKs for the same API

This entire blog — document types, blocks, media, and the two posts you're reading — was modeled and published through the Umbraco MCP server, live, without a single migration file. That's not a party trick; it's what happens when the protocol does its job.
