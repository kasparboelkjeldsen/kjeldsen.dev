Why MCP Is Awesome: A New Contract Between AI and Your Tools

Every AI assistant eventually hits the same wall: it's great at reasoning, mediocre at knowing which button to press. For years, the answer was bespoke integrations — one plugin per app, one schema per vendor, glued together with hope. The Model Context Protocol (MCP) replaces that patchwork with a single, open contract: any client that speaks MCP can discover and call tools from any server that implements it, without either side knowing the other exists in advance.

What makes this genuinely exciting isn't the transport — JSON-RPC over stdio or HTTP is unglamorous by design. It's the discovery. A server exposes its tools, resources and prompts with real schemas, and a client can list them at runtime. That means an assistant working inside Umbraco.Bench can ask "what can I do here?" and get back a live answer: create a document type, move a data type, publish a page — the exact vocabulary this project's own MCP server exposes, no bespoke glue code required on either side.

It also means the boundary between "the model" and "the system" gets a lot cleaner. Instead of an LLM improvising a raw HTTP call against an API it half-remembers, it calls a named tool with a validated payload, and gets back a structured result it can reason about. Errors are typed. Side effects are explicit. Nobody has to trust the model to have memorized your OpenAPI spec correctly.

“MCP is the difference between an assistant that guesses your API and one that reads your menu.”

— Anonymous platform engineer

None of this required us to write a single migration or hand-roll a content API for this blog. Every document type, data type, block, and piece of content on this page was created by an agent talking to Umbraco's own MCP server — the same server you'd point any other MCP-aware client at. That's the real pitch: not a smarter model, but a common language that lets any sufficiently capable model operate your tools safely.
