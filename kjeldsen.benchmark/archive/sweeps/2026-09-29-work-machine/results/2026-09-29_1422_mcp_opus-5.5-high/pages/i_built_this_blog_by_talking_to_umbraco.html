I built this blog by talking to Umbraco

No backoffice clicks, no migration scripts: just an agent, the Umbraco MCP server and a clear set of house rules.

The page you're reading was built by an AI agent in a single session. It started with an empty Umbraco install and a .mcp.json that pointed at the local Umbraco MCP server. Every step went through that server's tools, which call Umbraco's Management API.

The order of operations

  1. Model the content. Five element types (Hero, Rich Text, Image, Quote and Blog Post List) were created with create-element-type and moved into the Blocks folder. Two block grid data types came next: one for the front page and one for posts. Then the Blog Front Page and Blog Post page types were added, with templates and allowed children.
  2. Create the content. The Unsplash photos were streamed straight into the media library with create-media. The front page and both posts were created and published as block grid JSON, and each one was read back to confirm it had saved.
  3. Write the views, last. ModelsBuilder only regenerates models when the site restarts. So the Razor was written only after the content was in place.

What made it work

Guardrails that live in the CMS. This project enforces its own rules. When the agent saved the new block grid data types at the root, a notification handler moved them into /Custom/Umbraco.BlockGrid. The agent didn't have to remember that rule, because Umbraco applied it.

Reading back after every write. Block grid values are nested JSON: a layout, content data and an expose list that all have to refer to the same keys. A mistake there fails quietly. Reading each document straight back showed that every block had been stored, and that the server had filled in details such as the media type alias.

Knowing each tool's quirks. update-document-type replaces the whole type, so the agent always fetched the current definition, merged its change and sent everything back. create-element-type has no parent folder option, so each block is created at the root and then moved into place.

Why this is awesome

Setting up a content model is usually an afternoon of clicking through the backoffice. Here it was a conversation. More importantly, the result is ordinary Umbraco: normal document types, normal block grids and normal published content, all exported to uSync and ready to commit. Nothing about it depends on the AI that built it.

That's what MCP does well. It doesn't replace your platform or lock you into a new one. It lets an assistant work with the platform you already trust, using the same API and permissions your editors already have.
