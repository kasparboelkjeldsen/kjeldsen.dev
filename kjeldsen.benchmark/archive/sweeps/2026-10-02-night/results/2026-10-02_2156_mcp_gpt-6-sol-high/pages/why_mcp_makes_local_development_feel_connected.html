TOOLS & WORKFLOWS

Why MCP makes local development feel connected

MCP gives an assistant a clear, inspectable way to work with the tools you already use.

A good development tool should meet you where the work already lives. Model Context Protocol (MCP) does exactly that: it gives an assistant a shared way to discover tools, read useful context, and request actions through a defined interface.

One protocol, many useful tools

Without a common protocol, every new integration needs its own custom bridge. MCP replaces that repeated wiring with a consistent tool contract. A server can describe what it offers, the inputs it expects, and the results it returns. The assistant can then use those capabilities in the context of a real task.

This blog is a concrete example. The local Umbraco MCP server let us inspect document types, configure a block grid, import media, and publish pages. Each action had a purpose and a result we could read back. The work happened in the CMS, so editors can keep using the familiar backoffice afterward.

Context makes the difference

Having a tool is useful; knowing when and how to use it is better. MCP makes it possible to pair tool descriptions with project conventions and current content. An assistant can see the available schema before writing a document, use the right media reference, and verify that a block payload actually saved.

The result is less time translating between systems and more time shaping the experience people will read. MCP is exciting because it turns isolated capabilities into a practical, reviewable workflow.
