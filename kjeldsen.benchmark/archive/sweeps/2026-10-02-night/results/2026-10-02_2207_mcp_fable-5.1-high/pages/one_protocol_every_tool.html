One protocol, every tool: why MCP is the USB-C of AI

28 September 2026 · Claude

Before MCP, every AI integration was a bespoke cable. The Model Context Protocol replaces that tangle with one plug that fits everything.

The integration tax

Every team that has wired an AI assistant into a real system knows the pattern. You write a connector for your CMS. Then one for the ticketing system. Then one for the database, the file store, the analytics API. Each one has its own authentication story, its own way of describing what it can do, and its own quirks that live in one developer's head.

That is the integration tax, and it is paid again for every new model, every new client and every new tool. The N-by-M problem is not a theoretical concern. It is why most "AI integrations" ship as a demo and never make it to production.

One plug

The Model Context Protocol (MCP) attacks the problem the way USB-C did for hardware. Instead of a cable per device, there is one standard connector. A tool exposes an MCP server once, describing its capabilities in a machine-readable form. Any MCP-aware client can discover and use those capabilities, with no custom glue.

The server tells the client what tools exist, what arguments they take and what they return. The client, which may be a chat assistant, an IDE or an autonomous agent, picks the right tool for the job and calls it. Authentication, transport and error handling are part of the protocol, so they are solved once, not per integration.

“Build the server once. Every client that speaks the protocol gets it for free.”

— The whole pitch, in one sentence

What this buys you in practice

  • Discovery instead of documentation. The agent asks the server what it can do. Nobody pastes an API reference into a prompt.
  • Typed arguments. Every tool ships a JSON schema. Bad calls fail at the boundary with a clear error instead of corrupting data downstream.
  • Swappable clients. The same Umbraco MCP server works from a terminal agent, a desktop assistant or a CI pipeline. Change the client, keep the integration.
  • Composable servers. An agent can hold a CMS server, a search server and a file server at the same time and move data between them in one conversation.

Why it sticks

Standards win when the cost of adopting them is lower than the cost of not adopting them. MCP crossed that line fast because the first server you write replaces a dozen one-off integrations, and because the protocol is small enough to implement in an afternoon. Umbraco's own MCP server is a good example: it maps the management API onto tools for documents, document types, data types, templates and media, and that is enough to build an entire site without touching the backoffice.

That is what makes MCP awesome. Not that it is clever, but that it is boring in the right way. One plug, every tool.
