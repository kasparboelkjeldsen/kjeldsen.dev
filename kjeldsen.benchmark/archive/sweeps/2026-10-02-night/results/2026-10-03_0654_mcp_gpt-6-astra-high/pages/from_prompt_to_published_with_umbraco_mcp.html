In practice

From a good idea to a published page.

A local Umbraco experiment shows how a connected assistant can handle the repetitive work while keeping content structured and editable.

02 October 2026 /3 min read

A useful tool should make a real task easier. So our test for MCP was straightforward: build a small blog in a local Umbraco project, write two articles, and use the CMS properly all the way through.

The result is the journal you are reading. Its content was created through the Umbraco MCP server, using a sequence that kept the content model, editorial work, and presentation in their proper places.

First, understand the shape of the site

The starting point was a running Umbraco instance and a published WWW repository. Before creating anything, the assistant inspected the existing document types and data types. That revealed what could be reused and what the blog needed.

The new model is deliberately small: a front page, a blog post type, and blocks for the hero, post listing, article header, and rich text. The front page and articles each have their own block grid, so editors see the blocks that make sense for that page.

Then, put real content in the CMS

The photographs were imported from the supplied local files into a media folder. The front page was created beneath WWW and given a domain so that it could answer at the site root. The articles were added below the front page and published.

This is where the connection is especially useful. A request that sounds like one task to a person becomes a series of explicit CMS operations: create a media item, set a property, save a document, publish it. The assistant can coordinate those steps without asking an editor to copy the same information between screens.

Read back what you wrote

A successful tool response is useful evidence, but it is not the whole check. Block grids contain linked identifiers for their layout and content. We read the saved documents back to confirm that those references, media selections, and published states survived the write.

This habit gives the workflow a practical feedback loop. Inspect, change, inspect again. If the stored result differs from the intention, fix that before building more work on top of it.

Automation is more useful when its results are easy to inspect.

Give the content a proper home on the page

Schema changes generate new C# models in this project, so the application must be stopped, built, and restarted before Razor uses them. The rendering code can then follow the project's normal pipeline: a page calls the block grid renderer, a block adapter prepares a plain model, and a ViewComponent renders the markup.

MCP handles the CMS work in this experiment; the project's normal build tools handle the presentation. Both parts matter. Publishing content does not, by itself, prove that a page renders correctly.

Keep the result useful tomorrow

The best part is what remains after the demonstration. The posts are editable documents. The images live in the media library. The listing can discover published child posts. Adding the next article continues the same workflow.

That is the kind of automation worth getting excited about: a little less repetitive work today, and a clear, familiar structure to build on tomorrow.
