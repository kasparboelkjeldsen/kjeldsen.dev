The bigger picture

One connection. A world of possibility.

Why MCP feels like a common language for your tools—and why that gives us more time to make things worth making.

03 October 2026 /3 min read

There is a particular kind of friction that every maker knows: you have a clear idea, but getting it into your tools means a dozen tiny detours. Find the right screen. Look up an identifier. Copy a value. Check which field accepts which format. Repeat.

Model Context Protocol, or MCP, makes a compelling promise for this kind of work: give an AI assistant a defined way to discover and use the capabilities of a connected application. In this local Umbraco project, that means an assistant can ask what content types exist, inspect their fields, and use named tools to create and publish content.

From a description to something you can use

An assistant without access to the CMS can suggest a blog structure. With the local Umbraco MCP server, it can help turn that structure into actual document types, blocks, media, and pages. The difference becomes tangible when you open the backoffice: the work is there, ready to inspect and edit.

This journal is a small example. Its front page lives beneath the WWW repository. Its articles are normal Umbraco documents. The photographs came from the project's local image collection and were imported into a media folder. Each of those steps used a tool exposed by the MCP server.

Less guessing, better questions

One of the most useful steps happens before anything is created. The assistant can read the existing schema. That makes it possible to reuse a text editor or image picker, choose a valid document type, and understand the shape of a block grid value before sending it.

That context matters. “Add an image” is a vague instruction until you know which media item to reference and which property expects it. Reading the application first turns a broad request into a concrete change that can be checked afterwards.

The exciting part is the shorter distance between an idea and an editable result.

The application still has a job to do

MCP does not replace Umbraco's content model, publishing system, or rendering conventions. Here, pages still render through Razor. Blocks still use Umbraco's block grid renderer. Editors still work with the same content in the backoffice.

That is a strength. A connected assistant can help with repetitive setup while the CMS remains the place where the content belongs. There is no separate pile of article HTML hiding in a script, and no new publishing system to learn.

Start with one useful connection

You do not need an elaborate demonstration to see the appeal. Create a page, attach a photograph, publish it, and read it back. Each successful step makes the workflow a little more direct.

For us, that is why MCP is awesome: it makes the tools we already use easier to work with, and leaves more attention for the ideas we want to put into them.
