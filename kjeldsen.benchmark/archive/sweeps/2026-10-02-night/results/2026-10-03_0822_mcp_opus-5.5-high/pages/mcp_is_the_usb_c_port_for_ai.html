MCP is the USB-C port for AI

Before USB, every device had its own plug. Before MCP, every AI integration had its own glue code. Here's why one open protocol beats a thousand bespoke connectors.

Dig through a drawer of old electronics and you'll find the history of connectors: barrel plugs, proprietary docks, mini-USB, micro-USB, and a dozen chargers that fit exactly one thing each. Every new device meant a new cable. USB-C didn't make devices smarter. It made them interchangeable.

AI assistants have had the same drawer problem. Want your model to read a database, open a ticket, or edit a web page? Someone had to write a custom integration for that specific model and that specific tool. With M models and N tools you end up maintaining M × N pieces of glue code, and every one of them breaks in its own way.

One plug, both directions

The Model Context Protocol (MCP) is an open standard that turns that M × N problem into M + N. A tool vendor writes one MCP server describing what their system can do. An AI application implements one MCP client. Any client can then talk to any server. Build once, connect everywhere.

What a server actually offers

An MCP server describes its capabilities in a way a model can discover at runtime. There are three main building blocks:

  • Tools: actions the model can take, such as create a document, run a query or upload an image. Each one has a name, a description and a JSON schema for its inputs.
  • Resources: read-only context the model can pull in, like files, records or API responses.
  • Prompts: reusable templates a server can offer for common tasks.

Because the schema travels with the tool, the model doesn't need to be trained on your API. It reads the description, works out the shape of the input and makes the call. Add a new tool to the server and every connected assistant can use it immediately.

Why open matters

Plenty of platforms have had plugin systems before. The difference is that MCP isn't owned by any one assistant. It's an open specification built on plain JSON-RPC, and it runs over standard transports: a local process talking over stdio, or a remote service over HTTP. That makes it cheap to adopt and safe to bet on. The server you write today works with the assistant you switch to tomorrow.

It also keeps you in control. The server decides which tools exist and what credentials they run with. The client decides when to ask a human for permission. The model never gets more access than the server explicitly hands it.

The takeaway

MCP is boring in the best possible way. It's a plug. And once everything shares the same plug, the interesting work moves from writing glue code to deciding what you actually want your tools to do.
