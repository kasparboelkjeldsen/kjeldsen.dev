Building this blog through MCP, without opening the backoffice

Every document type, block, image and word on this site was created over the Model Context Protocol. Here is how it went and what surprised me.

The brief

Build a small blog in Umbraco: a front page that lists posts, two posts, and images from a folder of Unsplash photos. The twist is that every step had to go through the Umbraco MCP server. No clicking around in the backoffice, no SQL, no migration code.

Modelling first

The first pass was pure content modelling. Five element types became the blocks you are reading now: a hero, rich text, an image with a caption, a pull quote and a list of blog posts. A block grid data type ties them together with column span options, so an editor can put two images side by side or let a quote sit at two thirds width. Two document types, Blog Front Page and Blog Post, carry that grid as their body.

Each of those was a single tool call with a JSON payload. The server validated it, Umbraco saved it, and ModelsBuilder wrote strongly typed C# classes to disk before the next call returned.

Then the content

With the schema in place, the posts themselves are just more JSON: a layout that says which block goes where, the content data for each block and an expose list so Umbraco knows the blocks are live. The images were imported from local files into a media folder, then referenced by key from the hero and image blocks.

What surprised me

  • Read it back. Block payloads fail quietly if the keys do not line up, so the habit of fetching a document right after writing it paid for itself immediately.
  • Whole-object updates. Updating a document type means sending every field. Forget one and it is gone. Get, merge, update.
  • Parallelism has limits. Nine simultaneous writes against a SQLite development database produced table locks. Two or three at a time was smooth.

The Razor came last

Only once the content looked right did the site get its views. That order matters: the running site holds the old models until it restarts, so writing views too early means compiling against types that do not exist yet. Model, fill, restart, render.

“The agent never opened the backoffice. It read the schemas, made the calls and checked its work.”
